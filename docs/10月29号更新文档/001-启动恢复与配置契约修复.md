## 加密转换的恢复协议

1. 在同一数据库的 OS 文件锁内，核验源数据库并完成 WAL checkpoint。
2. 写入并刷新 `<database>.conversion.json` 的 `preparing` 意图；记录源/目标模式、随机 operation ID、源 SHA-256 与表行数，不保存密钥或用户原文。
3. 保存权限为 `0600` 的源数据库保护副本，导出目标格式。完整性、各表行数均一致后，刷新文件，持久提交 `ready` 阶段及目标 SHA-256。
4. 替换数据库，再原子提交 `.encryption.json` 的目标模式。目标确认且 marker 提交成功后，清理转换临时文件、保护副本和恢复记录；运行时随后才能打开数据库。
5. 重启发现 `ready`：实际数据库匹配目标则补交 marker；源与暂存目标匹配则继续替换。`preparing` 且源仍完整时清理部分输出并重新转换。实际文件无法确认、但保护副本有效时恢复源并停止此次启动，提示重启重试；材料均无效时保留现场并报错。

转换与 Alembic 迁移由 `upgrade_db` 在同一个 `migration_lock` 中连续执行，公开的 `apply_pending` 也获取同一把锁，不嵌套获取非重入锁。没有新增迁移，head 仍为 `024`。恢复/转换只读取原有系统凭据；缺密钥不自动生成新密钥。

加密协议中的文件与 JSON 写入都先 flush/fsync，再关闭句柄后 replace。POSIX 另外 fsync 目录；Windows 使用文件刷新与关闭句柄后的替换，没有声称便携 Python API 能提供 Windows 目录 fsync。这些措施覆盖已注入的进程中止与文件异常，不等同于任意存储硬件故障的保证。

## 备份恢复与加密切换

恢复任务持有维护门，等待其他已入场请求退出，然后停止拥有数据库的任务与连接。保护副本、备份替换、校验/迁移及回滚均有明确收尾归属。调用方反复取消时，仍需等待正在修改文件的 worker 完成，确认文件终态后才决定是否重建。

普通失败在验证回滚并重建成功后恢复服务；无法确认回滚或重建成功时保留保护副本，运行时保持失败与拒绝新写入状态。并发第二次恢复会被拒绝。待加密/解密或未完成转换记录存在时，恢复在停止运行时之前被拒绝，要求先重启完成转换，避免只回滚数据库而遗漏加密 metadata。

恢复链验收覆盖协程取消与 I/O 异常；本项没有增加恢复过程的跨进程崩溃 journal。加密转换的进程强杀验收属于上一节的独立协议。

## 配置与事件派发

保存配置、删除密钥会使旧探测失效。探测不通过可重新注册的共享 writer role 路由，而使用不可变配置对应的 provider；网络返回后再次检查 revision。设置页对保存/测试进行互斥，并按回执归属接受结果，保留用户在等待期间的新编辑。

持久化失败时，当前进程已经应用的配置可继续使用，界面明确说明尚未保存到磁盘，并提供重试路径。旧 JSON 在临时文件写入或替换失败时仍可解析且保持原内容；密钥仍由凭据存储管理，不写入普通配置 JSON。凭据存储和 JSON 文件不是一个事务，回执按实际部分成功结果报告。

### 设置 API 的新增字段

路由前缀为 `/api/v2/math-tutor/desktop`。原有配置字段保留；以下为新增的归属与持久化回执。

| 字段 | 含义 |
|---|---|
| `revision` | 本进程已应用配置的单调版本；JSON 成功提交时一同保存，重启从最近持久版本继续。失败写入的内存版本仍向前推进。 |
| `epoch` | 本次运行的随机标识，防止旧窗口在服务重启后误匹配相同数字版本。该值不是凭据。 |
| `current_revision` | 生成响应时的当前版本；与结果 `revision` 不同或 `accepted=false` 时，客户端不能将结果合并为当前配置。 |
| `accepted` | 当前版本匹配、且探测快照未失效时为 `true`；为 `false` 时整份回执不能合并。 |
| `operation_id` | 回显调用者的操作标识，用于请求归属；不是持久幂等 ledger，不能据此假定未知结果已回滚。 |
| `persisted` | `accepted=true` 时表示本次生效配置是否已写入普通配置 JSON；`false` 不否定已经应用的运行配置。拒绝的回执整份忽略。 |
| `persistence_error` | 固定错误码 `config_write_failed`、`persistence_unavailable`，或无错误时的 `null`；不含路径、密钥或异常堆栈。 |

`GET /settings` 返回配置及回执。`PUT /settings` 在原有入参外接收 `expected_revision`、`expected_epoch`、`operation_id`；版本不匹配时返回 409，客户端重新读取后再决定是否保存。`POST /model/test`、兼容路由 `POST /settings/test-connection`、`DELETE /settings/api-key`、`POST /settings/onboarding/skip` 接收 `{revision, epoch, operation_id}`。探测回执另外包含 `provider_id`，旧版本探测不能返回当前成功状态。

例如，运行中应用成功但 JSON 提交失败时，响应包含 `accepted=true, persisted=false, persistence_error="config_write_failed"`。设置页推进已确认的运行配置基线，保留提交之后的新编辑，并提示重试；初次配置页的保存与暂时跳过都保留表单，不把此结果当作持久完成而跳转。网络失败导致结果未知时保留输入，提示重新读取确认。

新入参允许省略以兼容旧调用者；服务端仍独立使用内部 mutation generation 与配置版本阻止陈旧探测发布。新客户端始终发送版本与运行标识。

relay 的重试时间与尝试上限语义保持不变。候选采用有预算的 keyset 扫描和跨轮游标，并限定每轮扫描水位，避免持续新事件反向饿死已到期重试。完全处于退避的队列会进入 idle 等待，relay 自己读取或写 ledger 不再触发自身忙轮询。
